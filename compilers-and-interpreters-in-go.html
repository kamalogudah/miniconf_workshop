How this workshop works

Every session builds directly on the last. You'll keep one Go module — nuru — open for the whole workshop, adding and changing files as you go. Nothing here is pseudocode: every listing on this page was compiled and run with go 1.22 before being written down.

What you need

  • Go 1.21 or newer installed (go version to check)
  • A terminal and an editor — nothing fancier required
  • ~6 months of Go under your belt: you're comfortable with structs, pointers, slices, maps, and interfaces

One module, six sessions

The language we're building is called Nuru — Swahili for "light", in the spirit of what a compiler pipeline does: it shines a light through your source code, one stage at a time, until nothing about it is a mystery. Nuru has integers, booleans, arithmetic, variables, conditionals, and first-class functions with closures. It's deliberately small, so you spend your time on how a language works rather than typing out a big spec.

Running the checks yourself Every code listing is followed by a terminal block showing the exact output you should see from go run .. If your output doesn't match, that's a more useful signal than any explanation — go back and compare your file against the listing before moving on.

The pipeline, end to end

Every session adds one stage. Source text goes in the top; a result comes out the bottom.

A second execution strategy: compile the AST to bytecode and run it on a small stack machine.

SESSION 02 1h 30m

The AST, and parsing expressions with precedence

A token stream is flat; code is not. 5 + 5 * 2 needs to become a tree where multiplication is nested inside the addition, not sitting next to it. This session builds the tree (the AST) and the parser that produces it — including the trick that makes precedence work.

  • Define Node, Statement, and Expression as Go interfaces
  • Model let, return, and bare-expression statements
  • Parse let/return with straightforward recursive descent
  • Parse arithmetic and boolean expressions with a Pratt (operator-precedence) parser
The core idea of Pratt parsing Every token that can start an expression gets a "prefix" parse function (numbers, identifiers, -x, !x). Every token that can continue one gets an "infix" parse function, tagged with a precedence. parseExpression parses the left-hand side, then keeps folding in infix operators for as long as the next operator binds tighter than the one it's currently inside. That one rule is what makes * nest inside + automatically.
STEP 1

Define the AST nodes

Create ast.go. Statement and Expression both embed Node, so anything that implements one also gives you TokenLiteral() and String() for free — String() is what lets us print a whole tree back out as source-like text, which is invaluable for debugging a parser.

ast.gonew file
STEP 2

Build the parser

Create parser.go. The Parser holds a current and a peek token (exactly like the lexer held a current and a peek character), plus two maps of parse functions keyed by token type.

parser.gonew file
Common gotcha In parseExpression, the loop condition is precedence < p.peekPrecedence() — strictly less than. If you write <= by accident, operators of equal precedence (like + and -) will parse right-associatively instead of left-associatively, and 10 - 3 - 2 will quietly evaluate to the wrong thing later.
STEP 3

Try it

main.gonew file
terminal

Look closely at ((10 * 2) + 3) — the parentheses in the printed output aren't from your source, they're String() making the tree's actual shape visible. That's the precedence climbing working correctly.

SESSION 03 1h 30m

Parsing control flow and functions

With statements and arithmetic working, this session extends ast.go and parser.go — the same two files from Session 2 — to handle if/else, grouped expressions, function literals, and function calls. No new files.

  • Add IfExpression, FunctionLiteral, and CallExpression nodes
  • Parse (...) grouping by reusing precedence, not a new AST node
  • Parse function literals and their parameter lists
  • Parse call expressions as an infix operator on (
The key insight: calls are infix add(1, 2) looks like it starts with add, but what actually matters to the parser is the ( that follows it — the same way + follows a left-hand side. So CallExpression is parsed by registering LPAREN as an infix parser with CALL precedence, higher than everything else. The "left" side it receives is whatever expression was being called.

SESSION 04 1h 30m

Making it actually run: the evaluator

Parsing gives you a tree; it doesn't give you an answer. This session introduces two new files — object.go for representing runtime values, and evaluator.go for walking the tree and producing them. This is where Nuru becomes a real interpreter.

  • Design an Object interface for runtime values (integers, booleans, null)
  • Write Eval as a big type-switch over AST nodes
  • Handle return by wrapping values so they can "bubble up" through nested blocks
  • Turn runtime problems (like 5 + true) into proper error values instead of Go panics
STEP 1

Define the object system

Create object.go. Every value Nuru produces at runtime implements Object. We reuse single shared instances for true, false, and null — there's no reason to allocate a new one every time, and it lets the evaluator compare booleans by pointer later.

object.gonew file
STEP 2

Write the evaluator

Create evaluator.go. Eval recognizes each AST node type and knows how to turn it into an Object. The two trickiest parts are return unwinding and error propagation — both are handled by giving ReturnValue and Error their own object types that the block-evaluation loop specifically checks for.

evaluator.gonew file
Why evalBlockStatement doesn't unwrap ReturnValue evalProgram unwraps a ReturnValue because a return at the top level ends everything. But evalBlockStatement deliberately leaves it wrapped — a return inside a nested if needs to keep bubbling up through each enclosing block until it reaches the top (or, from Session 5 onward, a function call). If the inner block unwrapped it early, an early return inside an if would only exit the if, not the whole function.

SESSION 05 1h 30m

Variables, function calls, and closures

The evaluator from Session 4 can compute expressions, but it has nowhere to put a variable. This session adds a new file, environment.go, and threads it through every Eval call — which is also what finally makes function calls, and closures, possible.

  • Build an Environment that maps names to values, chained to an outer scope
  • Evaluate let statements and identifier lookups
  • Evaluate function literals and calls — and see exactly where closures come from
Where closures actually come from A Function object doesn't just store its parameters and body — it stores the *Environment that was active when it was defined. Every time you call it, we create a new environment for the call's local variables, but chain it to that captured one. That chain is the entire mechanism behind closures; there's no separate "closure" feature to build.

Reading applyFunction closely extendFunctionEnv creates a new environment chained to fn.Env — not to whatever environment the call site happens to be in. That's deliberate: it's what gives you lexical scoping (a function sees the variables that were visible where it was written) instead of dynamic scoping (where it would see the caller's variables). unwrapReturnValue then does the opposite job of Session 4's evalBlockStatement: it stops a return from bubbling any further once it's escaped the function it belongs to.

A genuine limitation, not a bug Notice counter() returns 1 every single time you call it, instead of counting up. Look closely at the body: let count = count + 1; — that let creates a new local binding on every call; it reads the outer count (always 0) and shadows it with a fresh one. Nuru, as built so far, has no way to rebind an existing variable — only to declare new ones. That's exactly what this session's exercise fixes.

SESSION 06 1h 30m

From tree-walking to bytecode: a compiler and a VM

The evaluator from Sessions 4–5 re-walks the AST every single time it runs — fine for a workshop, expensive in production (it's part of why real language runtimes compile). This closing session builds a second, independent execution engine: a compiler that turns the AST into flat bytecode, and a virtual machine that executes it on a stack.

A fresh, smaller sub-project To keep this session self-contained, build it in a new folder (or new module) alongside nuru — reuse token.go, lexer.go, ast.go, and parser.go as they stood at the end of Session 3 (before variables or functions existed), plus a small, VM-specific object.go. We're deliberately not (yet) compiling variables or function calls to bytecode — that's real, meaty follow-up work, sketched out in Next steps.
  • Understand why bytecode + a VM can outperform tree-walking
  • Define an instruction format: an opcode plus fixed-width operands
  • Write a compiler that walks the AST once and emits instructions
  • Handle if/else using jump instructions with back-patched targets
  • Write a stack machine that executes the bytecode
STEP 1

A minimal object system

The VM needs runtime values too — a smaller version of Session 4's object.go:

object.gonew file
STEP 2

Define the instruction format

Create code.go. An instruction is one opcode byte followed by however many operand bytes that opcode needs — OpConstant takes a 2-byte index into a constant pool; OpAdd takes no operands at all, because it just acts on whatever's already on the stack. The Definition map is what lets Make and the disassembler stay generic instead of one giant switch each.

code.gonew file
STEP 3

Write the compiler

Create compiler.go. It walks the same AST from Sessions 2–3, but instead of computing a value, it emits instructions. The one genuinely new idea is how if/else compiles: we emit a conditional jump with a placeholder target, compile the branch, and only then go back and patch in the real jump offset — because we don't know how far to jump until we've compiled what we're jumping over.

compiler.gonew file
The "<" trick Look at how node.Operator == "<" is handled: instead of adding a whole new OpLessThan opcode, the compiler just compiles the right-hand side first, then the left, then emits OpGreaterThan. 3 < 5 compiles as if it were written 5 > 3. One less opcode for the VM to implement, for free.
STEP 4

Write the VM

Create vm.go. It's a simple stack machine: an instruction pointer walks the bytecode, and each opcode pops however many operands it needs off the stack and pushes its result back on.

vm.gonew file
Watch the instruction pointer around jumps case OpJump: sets ip = pos - 1, not ip = pos. That's not an off-by-one bug — the for loop's own ip++ runs right after the switch, so subtracting 1 first is what makes execution actually land exactly on pos on the next iteration.

Where to go from here

Nuru is deliberately small. Every item below is a real, well-scoped extension you now have the foundation to tackle on your own — roughly ordered from "next weekend" to "next few weekends."

Grow the language

  • String and array literals, plus indexing (arr[0])
  • A hash/map literal type
  • && / || with short-circuit evaluation
  • A handful of built-in functions (len, print)
  • for loops, or a while-style construct

Grow the VM

  • Compile let and identifiers using a symbol table
  • Compile function literals and calls — this needs frames, not just a flat stack
  • A garbage collector, once the object graph gets cyclic
  • Benchmark the VM against the tree-walking evaluator on something like recursive Fibonacci — the gap is the whole point of Session 6
Further reading This workshop's structure — lexer → Pratt parser → tree-walking evaluator → bytecode compiler and VM — closely follows the path taken in Thorsten Ball's Writing An Interpreter In Go and its sequel, Writing A Compiler In Go. If any single session here clicked, those books go several times deeper into the same ideas. Bob Nystrom's Crafting Interpreters (free online) covers the same ground again in a different implementation language, which is a genuinely good way to see which parts of this design are fundamental and which were just one author's choice.
